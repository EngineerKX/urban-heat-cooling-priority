## 2. Core migration — built and verified locally, in dependency order

Each piece below was implemented, then immediately tested against real
local data before moving to the next:

- **`tfrecord` package validated standalone first** (the single highest-
  risk substitution in the whole plan) — installed `tfrecord[torch]`,
  wrote a throwaway script parsing the real on-disk `.tfrecord.gz` shards
  (`data/interim/unet_patches/{train,inference}/`) via
  `tfrecord.torch.dataset.TFRecordDataset(..., compression_type="gzip")`.
  Result: patch counts matched `mixer.json`'s `totalPatches` exactly
  (1066/1066 both dirs), all bands correct shape/dtype, band value ranges
  physically plausible (S2 reflectance 0-13194, NDVI/NDBI/NDWI in [-1,1],
  `wc_class` in {0-4}). De-risked the whole migration before writing any
  other code.
- **`src/utils/gcs.py`** (new) — extracted `_gcs_client()` out of
  `src/ingest/gee.py` into a public `get_client()`, added
  `upload_file`/`blob_exists`/`blobs_exist_with_prefix`/`download_text`/
  `upload_text` (no general-purpose upload helper existed before this;
  everything was GEE-export-driven). `gee.py`'s `export_patches_to_gcs`/
  `export_geotiff_to_gcs` now call these instead of duplicating client
  logic. Verified with a real upload/download/delete round-trip against
  the live bucket before building anything on top of it.
- **`src/landcover/unet_model.py`** (new) — pure PyTorch `nn.Module`
  port: `UNetBackbone` (3-level encoder-decoder, same `base_filters`
  doubling as the Keras version) + `UNet` (adds a 1x1 classification
  head, returns raw logits — no softmax layer, since
  `nn.CrossEntropyLoss` applies log-softmax internally and is more
  numerically stable; callers needing probabilities apply
  `torch.softmax` explicitly). Channels-first `(N, C, H, W)`, a
  deliberate departure from Keras's channels-last. Verified immediately
  with a forward-pass shape test (`(2,4,128,128)` output, 1,927,428
  params) before writing any data/training code around it.
- **`src/landcover/unet_data.py`** (new) — `build_training_stack`,
  fingerprint/cache helpers (unchanged logic, ported as-is), and the new
  GCS-cache-aware `export_training_patches`/`export_inference_patches`
  (see §3) plus `read_raw_patches()` — the shared low-level TFRecord
  reader used by training, inference, *and* the CNN's patch builder
  (previously duplicated 3x as near-identical `tf.io` blocks across the
  old `unet.py` and `cnn_patches.py`).
- **`src/utils/torch_train.py`** (new) — `train_loop()`, one shared
  training loop for both U-Net and CNN (Keras's `.fit()` +
  `EarlyStopping(restore_best_weights=True)` has no direct PyTorch
  equivalent; hand-rolled epoch/batch loop, per-pixel-weighted loss
  applied via `(raw_loss * weight).sum() / weight.sum()` rather than a
  class-`weight=` kwarg, best-checkpoint tracking via `copy.deepcopy`).
  Auto-selects `cuda` if available else `cpu`.
- **`src/landcover/unet_train.py`/`unet_infer.py`** (new) — training
  entry point (designed to run in Colab) and CPU inference/reconstruction
  (designed to run locally), split apart so each only needs the
  dependencies it actually uses.
- **End-to-end local smoke test** (before any Colab involvement): trained
  a real 2-epoch U-Net on the real local patches, saved, reloaded with
  `map_location="cpu"`, ran full-Singapore batched inference (1066
  patches) + tile reconstruction + probability raster — all passed on

- **CNN heat model split the same way**: `src/heat_model/{cnn_model,cnn_data,

  synthetic fixture rewritten to match the new layout — all 3 assertions

- **`src/utils/seed.py`**: `tf.random.set_seed` → `torch.manual_seed` +
  guarded `torch.cuda.manual_seed_all`.
- Deleted `src/landcover/unet.py`, `src/heat_model/cnn_patches.py`,
  `scripts/train_landcover_unet.py`, `scripts/train_heat_model_cnn.py`

## 3. GCS as a training-data cache, not just a model store

New design element, surfaced by a direct user question ("what about GEE,
every time training need to re-export?") mid-review: Colab's `/content`
disk is empty every session, so the existing local-disk skip-if-exists
cache alone would force a full multi-minute-plus GEE export on *every*
Colab run, even a same-data hyperparameter-only retrain.

- `unet_data.py::export_training_patches` now checks a **fingerprint-keyed
  GCS prefix** (`unet_train_patches/{sha256-of-validation-csv}/...`)
  before running the GEE export — download from GCS if already there,
  export only if genuinely new. Changed the existing flat prefix
  (`unet_train_patches/unet_train.*`, no versioning) to this nested,
  fingerprint-scoped one.
- `export_inference_patches` gets the same treatment keyed by plain
  existence (no natural fingerprint source for inference's inputs).
- New `--force-export` param on both, alongside the existing `--force`.
- `scripts/pull_models.py`/`push_models.py` (new) — hash-verified GCS
  sync for trained model artifacts, deliberately using a *different*
  sidecar (`models/{stem}.sha256`) from the existing training-fingerprint
  sidecar (`{stem}_fingerprint.txt`), since they mean different things
  (has-the-artifact-changed vs. was-this-trained-on-current-data).
  Round-tripped against the real bucket: push→skip-on-match→delete-local→
  pull→verify→pull-again-skips→`--force`-redownloads, all confirmed
  working before any real model existed.
- MLflow sync (the "i still need mlflow" correction): `src/utils/experiment_tracking.py`
  gained `export_run_summary()`/`import_remote_runs()` — Colab notebooks
  still call the existing `start_run()` for in-session visibility, then
  export params + per-epoch metrics history to GCS
  (`training_runs/{model}_{timestamp}.json`); `pull_models.py` re-imports
  any new ones into the local `mlflow.db` via `mlflow.log_params`/
  `log_metric(..., step=i)`, idempotently (a local
  `mlflow_imported_runs.txt` manifest, gitignored). Verified end-to-end
  with a fake run: uploaded, imported once, second import correctly
  no-op, confirmed queryable via `mlflow.search_runs` afterward, then
  cleaned up.
- Real bucket layout checked directly (not assumed) before designing new
  prefixes — ~796 MB across 8 objects at the time, confirming storage
  cost is negligible regardless of usage pattern; new prefixes added
  (`models/`, `training_runs/`, `training_inputs/`) documented in both
  the plan and this log.

## 4. Colab notebooks — built, then debugged live against a real session

`notebooks/colab_training/train_unet.ipynb` and `train_heat_cnn.ipynb`
generated programmatically (direct JSON construction + `ast.parse`
validation on every code cell, since the `Edit` tool refuses `.ipynb`
files directly) mirroring the deleted scripts' GEE setup logic. Every
import in both notebooks individually verified to resolve against the
real local environment before considering them done.

Real execution then surfaced four issues no amount of static review would
have caught, each fixed and re-verified against the live Colab session:

1. **`pip install -q -r requirements-colab.txt` → "No such file or
   directory."** Root cause (first pass): the shell-magic cell doesn't
   reliably inherit a prior cell's `os.chdir(REPO_DIR)` across cell
   boundaries in this VS Code↔Colab setup. Fixed by using IPython's
   `{REPO_DIR}` interpolation for an absolute path instead of relying on
   cwd state. Root cause (second pass, same error after the first fix):
   `requirements-colab.txt` itself didn't exist on the Colab VM yet
   because **none of this session's work had been pushed to GitHub** —
   the notebook's `git clone` pulls from the remote, which is a
   completely separate tree from the local Windows checkout. Fixed by
   committing (`66e8fd6`) and pushing.
2. **`pip`'s dependency resolver reported real conflicts**: Colab's own
   preinstalled `google-colab` package requires exact `google-auth`/
   `requests` versions, and `numba` requires `numpy<2.1` — all three
   overridden by this project's locally-pinned versions in
   `requirements-colab.txt`. Fixed by removing those three pins from
   `requirements-colab.txt` specifically (documented in a header comment
   so nobody re-adds them without understanding why) — committed as
   `ff26f84` alongside item 3 below.
3. **`google.colab.files.upload()` hung indefinitely** at the auth cell.
   Root cause: this Colab API depends on a JS/widget bridge specific to
   Colab's own web frontend (colab.research.google.com); VS Code's
   notebook renderer, even though genuinely connected to a real Colab
   kernel, doesn't implement that bridge, so the upload button never
   renders and the cell waits forever for a callback that can't arrive.
   A prior attempt to use the VS Code Colab extension's own Secrets UI
   (hunting through the Command Palette — "Colab: Focus on Resources
   View" etc.) also didn't turn up a working path. Fixed by switching to
   `getpass.getpass()` — plain Jupyter stdin protocol, frontend-agnostic,
   confirmed working via a real successful training run same day. Also
   deliberately avoided a base64-paste-into-cell-source alternative
   design, since that would risk a live credential getting saved into
   the committed (public!) `.ipynb` file if the user forgot to clear the
   cell before saving — `getpass` never echoes or persists the typed
   value into the cell's saved source or output.
4. **`%pip` vs `!pip`**: VS Code's Jupyter extension auto-converted the
   notebook's `!pip install` cell to `%pip install` at some point during
   live use (a known IPython-recommended-magic nudge) — the committed
   notebook was updated to match what was actually confirmed working,
   rather than fighting the auto-conversion.

All four fixes committed and pushed (`ff26f84`).

## 6. The `force_retrain` same-session trap — hit twice

User asked to retrain U-Net to see if results differ. First retrain
attempt: GCS timestamps for `models/unet_landcover.pt` didn't change at
all after a "finished" notebook run. Root cause: `train_unet(...,
force_retrain=False)` (the notebook's default) found a cached model
already on that specific Colab VM's disk (same session reused from the
first run, so the earlier run's output was still sitting in `/content`)
with a matching training-data fingerprint, and silently reloaded it
instead of retraining — `push_models.py` then correctly no-op'd too
(identical weights → identical hash → "already matches, skipping").

Fixed by editing the training cell's `force_retrain=False` → `True`
(directly, via the same JSON-manipulation approach used for the notebook
generation, since `Edit` refuses `.ipynb` files) plus correcting a
now-stale comment that still described the old default's behavior. This
also surfaced during a *third* retrain later in the session (§7) — same
root cause, same fix (this time already set to `True`, so no code change
needed, just confirmation the GCS timestamp genuinely moved before
proceeding with the pull/compare pipeline).

## 7. Three independent U-Net retrains — the real multi-run comparison

User asked to compare results after retraining, prompting `models/_backup_unet_run1/`
to be created first (model `.pt`, rasters, evaluation CSVs, a `SUMMARY.txt`
with the key numbers) before any retrain happened, specifically so the
first real run's results wouldn't be silently overwritten and lost. The
same backup was repeated for run 2 and run 3 as each new retrain
completed, each verified against a genuinely new GCS timestamp before
pulling (avoiding comparing a run against itself, per §6's gotcha).

Full pipeline run 3 times (pull → `run_landcover_unet_inference.py` →
`build_landcover_ensemble.py --force` → `evaluate_landcover_classifiers.py`):

| | accuracy | macro-F1 | bare_f1 (unet) |
|---|---|---|---|
| Run 1 | 79.3% / ensemble 77.8% | 0.641 / ensemble 0.675 | 0.143 |
| Run 2 | 77.8% / ensemble 76.3% | 0.620 / ensemble 0.643 | 0.133 |
| Run 3 | 76.3% / ensemble 76.8% | 0.636 / ensemble 0.668 | 0.211 |

Two real findings emerged only because 3 runs existed instead of 1
(detailed reasoning given directly to the user, reproduced here for the
record):

- **Ensemble is not reliably "the best."** Compiling worst/best across
  all 4 available runs (TF + 3 PyTorch) × 2 metrics (8 comparisons): RF
  was worst on accuracy in **4/4** runs, U-Net was worst on macro-F1 in
  **4/4** runs, ensemble was worst on **0/8** — but also only best in
  6/8, not all 8. The defensible justification for keeping ensemble as
  the production classifier, given this data, is "never the worst"
  (hedges against whichever component is having a weaker session), not
  "always the best."
- **PyTorch ensemble consistently underperforms the original TF ensemble**
  by ~2-3.5 points across all 3 runs (76.3-77.8% vs. TF's 79.8%) — a
  reproducible pattern, not noise, even though individual U-Net accuracy
  is comparable-or-better than TF's. Hypothesized (not confirmed) to be a
  softmax-probability-calibration difference between the frameworks'
  trained models affecting the soft-vote average, distinct from argmax
  accuracy. Flagged as an open item in the master prompt.
- Separately confirmed: the accuracy spread *between* RF/U-Net/ensemble
  (~75-80%) is roughly the same size as the spread from retraining U-Net
  alone 3 times (76.3-79.3%) — i.e. model-choice differences here are
  within the same noise band as pure retraining variance, echoing the
  project's own pre-existing S6 confidence-bands finding that adjacent
  ranked subzones aren't statistically distinguishable either.
- User asked whether redoing the (admittedly "fast, for fast deployment")
  hand-labeling would help — answered and confirmed against the actual
  data: no, for the two findings above specifically (both showed up under
  an unchanged, fixed label set across all compared runs), but plausibly
  yes for general noise reduction, particularly evidenced by `bare_f1`'s
  volatility (0.133-0.229) across the 3 runs on this small/ambiguous
  class. Decision on whether to relabel not made this session.

Separately, `scripts/build_hotspot_clusters.py --force` was re-run to
confirm S4 is genuinely unaffected by the U-Net retrain (predicted from
reading the code before running it, then confirmed): K-means k=4
(silhouette=0.342) and GMM k=3 (silhouette=0.297) came back byte-identical
to the pre-migration numbers, since clustering never uses the land-cover
model as an input — only the downstream land-cover-coherence check
(which does use the ensemble raster) reflects the new model, with the
same qualitative finding (hottest cluster = most built-up ✅, ≠
least-vegetated cluster ⚠️) as before.
