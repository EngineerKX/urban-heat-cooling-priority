## 1. Diagnosing the "convert to TF" request before touching code

Two things worth surfacing were checked before starting:

- **The long-path pip error isn't PyTorch-vs-TensorFlow specific.** It's a
  generic Windows `MAX_PATH` (260-char) limitation, made worse by this
  repo's already-deep OneDrive path. Confirmed by actually trying to
  install `tensorflow` locally and hitting the *exact* reported error on
  `tensorflow\include\external\envoy_api\...\client_side_weighted_round_robin.upb_minitable.h`
  — pip's own error message even names Windows long-path support as the
  cause.
- **The original TF→PyTorch migration reason doesn't block this.** Found
  in `docs/MIGRATION_PLAN_2026-08-05_1808.md`: the real driver was *"native
  Windows TensorFlow lost GPU support after 2.10"* — a GPU-only limitation.
  Training already happens exclusively on Colab (GPU, framework-agnostic)
  and local machines already only do CPU inference, so this doesn't apply
  to the revert.

Fix for the actual blocker (user ran these, not me — needs Administrator):

```
reg add "HKLM\SYSTEM\CurrentControlSet\Control\FileSystem" /v LongPathsEnabled /t REG_DWORD /d 1 /f
git config --global core.longpaths true
```

Reboot required. After that, `pip install tensorflow` (and the full
`requirements.txt`) installed cleanly — confirmed by retrying the exact
same install that failed before.

## 2. The TensorFlow/Keras port itself

Planned via `EnterPlanMode` (three parallel `Explore` agents: current
PyTorch pipeline, the frozen `snapshot/tensorflow` branch — confirmed to be
a strict linear ancestor of `kxbranch`, not a side branch — and every
downstream consumer of the two trained models), then executed directly.

**Rewritten as Keras (functional API), channels-last**:
- `src/landcover/unet_model.py`, `src/heat_model/cnn_model.py` — same
  3-level encoder-decoder, same `base_filters` doubling, same skip
  connections as the PyTorch version, just Keras layers instead of
  `torch.nn.Module`.
- `src/landcover/unet_data.py`, `src/heat_model/cnn_data.py` — TFRecord
  parsing swapped from the `tfrecord` PyPI package (PyTorch-only, no native
  TF reader) to native `tf.data.TFRecordDataset` + `tf.io.parse_single_example`
  — a net simplification, one fewer dependency. Arrays flipped from
  `(N,C,H,W)` to `(N,H,W,C)`.
- `src/landcover/unet_train.py`, `src/heat_model/cnn_train.py` —
  `model.compile()` + `model.fit(..., callbacks=[EarlyStopping(restore_best_weights=True)])`
  replacing the hand-rolled PyTorch epoch/batch loop.
- `src/landcover/unet_infer.py`, `src/heat_model/cnn_infer.py` —
  `tf.keras.models.load_model()` replacing `state_dict` reconstruction;
  simplified signatures (a `.keras` file embeds its own architecture, no
  `in_channels`/`base_filters` kwargs needed anymore).
- Deleted `src/utils/torch_train.py` wholesale (117 lines) — Keras's
  built-in `.fit()` replaces the entire hand-rolled training loop it
  existed for.
- `src/utils/seed.py` — `torch.manual_seed` → `tf.random.set_seed`.
- `config/settings.py` — `UNET_MODEL_SAVE_PATH`/`CNN_MODEL_SAVE_PATH`
  `.pt` → `.keras`.
- `scripts/push_models.py`/`pull_models.py` — the hardcoded `.pt` GCS
  blob-name literals → `.keras`.
- `requirements.txt`/`requirements-colab.txt` — `torch`/`tfrecord` swapped
  for `tensorflow`.
- Both Colab notebooks, `SETUP.md`, `tests/test_model_architectures.py`.

**A real gap the plan missed, caught mid-implementation**:
`src/heat_model/counterfactual.py` (`class_mean_feature_vectors`,

indexing (`X[:, :n_bands]`, `edited[:n_bands][:, edit_mask]`) — the
original plan had marked this file "not touched, framework-agnostic,"
which was wrong. Fixed as part of the same port; channels-last actually
*simplified* the indexing here (no more `moveaxis`/`newaxis` gymnastics).

**Verification, local**: `pip install -r requirements.txt` clean;
`tests/test_model_architectures.py` and
`tests/test_heat_model_counterfactual.py` both pass; every rewritten

## 8. Full evaluation run, and a real hybrid-vs-U-Net finding

User asked for "evaluation portion." Ran the full local chain: pulled both
new `.keras` models, regenerated `unet_landcover.tif`/`_prob.tif` with the
new model, force-rebuilt the ensemble raster, ran
`evaluate_landcover_classifiers.py` and `diagnose_heat_model.py`.

**Formal land-cover results**:

| model | accuracy | macro F1 | bare F1 |
|---|---|---|---|
| RF | 65.6% | 0.611 | 0.368 |
| U-Net | 70.3% | 0.547 | **0.000** |
| Ensemble/hybrid | 69.6% | **0.652** | 0.417 |

**CNN/XGBoost counterfactual cross-check**: 3/3 demo subzones (TUAS NORTH,
GUL CIRCLE, CHIN BEE) agree on cooling direction between the two
independently-built models.

**Follow-up discussion, "why is ensemble weaker?"** — pulled the actual
confusion matrices rather than speculating: the hybrid is only 2 points
worse out of 296 (statistical noise, SE≈2.7pp), and the trade is real and
favorable — it rescues 5/11 "bare" points U-Net structurally can never
predict (U-Net has zero recall on that class) at the cost of 8 points where
RF's built-up/bare confusion outvotes U-Net's otherwise-correct call. Net:
macro-F1 (which doesn't let a model get a free pass by ignoring a class
entirely) clearly favors the hybrid; raw accuracy is a coin-flip either way.

**"Only ~70% accuracy" discussion**: attributed to two real, checkable
causes rather than a vague "needs more tuning" — a thin/imbalanced label
set (300 points, only 11 "bare") and a minimal 9-band feature set with
little to separate spectrally-similar classes (built-up vs. bare).
Recommended class-weighted loss as the cheapest first experiment,
targeted relabeling as the highest-leverage one; not yet implemented
(user: "not at the moment").

## 10. "Ensemble" → "hybrid" rename throughout the codebase

User: their lecturer's rubric defines *ensemble* = multiple instances of
the *same* model type, *hybrid* = different model types working together
— RF (trees) + U-Net (CNN) is a hybrid under that definition, not an
ensemble, and the code's naming didn't match. Confirmed this wasn't just
grading semantics: `scripts/build_landcover_ensemble.py`'s own docstring
already said *the "Hybrid ML/ensemble" deliverable named in the project
proposal* — the proposal had already called it "Hybrid ML," the code just
never caught up.

**Scope**: 3 files renamed (`src/landcover/ensemble.py` → `hybrid.py`,
`scripts/build_landcover_ensemble.py` → `build_landcover_hybrid.py`,
`tests/test_landcover_ensemble.py` → `test_landcover_hybrid.py`), every
identifier (`ENSEMBLE_RASTER_PATH`→`HYBRID_RASTER_PATH`, `build_ensemble()`
→`build_hybrid()`, `ENSEMBLE_RASTER_GCS_PREFIX`→`HYBRID_RASTER_GCS_PREFIX`,
etc.), 2 data files on disk (`ensemble_landcover.tif` →
`hybrid_landcover.tif` + `_prob.tif`), evaluation-output filenames
(`confusion_matrix_ensemble.csv` → `..._hybrid.csv`, regenerated, old ones
deleted), MLflow run naming (`evaluate_ensemble`→`evaluate_hybrid`),
Streamlit UI labels, `SETUP.md`, both Colab notebooks, and every
docstring/comment across `src/`, `scripts/`, `app/`, `tests/`,
`validation/` — roughly 28 files total.

**Deliberately left alone**: `from sklearn.ensemble import
RandomForestRegressor` in `run_week1_gates.py` — that's scikit-learn's own
module path, and RF's bagged trees genuinely are a same-model-type
ensemble under the stated definition, so it's already correctly named.
Historical `notebooks/Colab Notebooks/*.ipynb` (pre-refactor reference
notebooks, same policy as the earlier TF port) also left untouched.

**Re-verified end-to-end after the rename**: full compile-check on every
touched file, `tests/test_landcover_hybrid.py`/`test_landcover_zonal.py`/
`test_classifier_evaluation.py` all pass, and re-running the formal
evaluation + `build_landcover_hybrid.py` produced byte-identical numbers
under the new names (69.6% accuracy, 0.652 macro-F1) — confirming the
rename touched naming only, not behavior.

## 13. Live-map "API KEY REQUIRED" tile fix

User shared a screenshot of the Streamlit app's Island Map page — every
basemap tile watermarked "API KEY REQUIRED." Root cause:
`app/pages/2_Island_Map.py` used `folium.Map(..., tiles="cartodbpositron")`,
and CARTO now requires a registered API key for their free basemap tiles;
unauthenticated requests get served this watermark instead of failing
outright. Fixed by switching to `tiles="OpenStreetMap"` (folium's built-in,
no key required).

**Verified with a real browser, not just "the code looks right"**: no
project-specific app-launch skill existed yet, `chromium-cli` wasn't
available on this Windows machine, so drove it directly via Python's
`playwright` package (already installed, v1.62.0) — launched
`streamlit run app/Home.py` in the background, polled port 8501, navigated
Playwright to `/Island_Map`, and took a real screenshot. Confirmed: real
OSM tiles (roads, place names, proper `© OpenStreetMap contributors`
attribution) render under the priority-score choropleth, zero
"API KEY REQUIRED" text anywhere on the page. Background Streamlit process
stopped afterward. **Not yet committed** — sitting as an unstaged change in
`app/pages/2_Island_Map.py` at the end of this session.
