## 1. What got built

The formal RF-vs-U-Net-vs-ensemble land-cover evaluation (previously the
project's highest-priority gap — "Hybrid ML/ensemble" is one of the 4
required course aspects, and no ensemble code existed at all):

- **`src/landcover/rf_baseline.py`**: added `classify_probability()` (RF
  in GEE `MULTIPROBABILITY` mode) + `RF_PROB_RASTER_PATH`. Fixed a
  pre-existing bug in `export_classified_raster()` (see §2).
- **`src/landcover/unet.py`**: `run_inference_and_reconstruct()` now
  optionally persists the per-class softmax array (already computed per
  patch, previously discarded after `argmax`) to a second probability
  raster. Added data-fingerprinting for both the training-patch cache and
  the model cache (see §2).
- **`src/landcover/ensemble.py`** (new): soft-voting ensemble — aligns
  RF's and U-Net's probability rasters onto a common grid (RF's own grid
  is the reference, since it's exported directly against the real
  boundary geometry; U-Net's is an artifact of the rectangular
  patch-export mechanism), averages per-class probabilities pixel-wise,
  argmaxes to a hard-label raster. Found and fixed a real masking bug
  here (see §2, the big one).
- **`validation/landcover_validation/classifier_evaluation.py`** (new):
  unified point-sampling (local rasterio + pyproj, same method for all
  three rasters — previously RF used GEE server-side `sampleRegions`
  while U-Net used local indexing, an asymmetric comparison) + confusion
  matrix / per-class precision-recall-F1, following the pattern already
  established in `validation/input_validation/labeling_agreement.py`.
- **`scripts/build_landcover_ensemble.py`**, **`evaluate_landcover_classifiers.py`**
  (new) — CLI entry points, same caching/fail-fast conventions as the
  rest of `scripts/`.
- **`tests/test_landcover_ensemble.py`**, **`test_classifier_evaluation.py`**
  (new) — the repo has no pytest/test framework, so these follow the
  existing codebase convention of a runnable script with printed
  pass/fail checks (see e.g. `build_training_region`'s sanity check),
  against small synthetic in-memory rasters. No GEE/GPU required.
- **`src/utils/experiment_tracking.py`** (new) — thin MLflow wrapper, see
  §4.
- **`app/pages/1_Label_Validation_Points.py`** — three UX fixes made
  while the user was relabeling (see §5).

## 2. Bugs found and fixed (in the order hit)

| # | Bug | Fix |
|---|---|---|
| 1 | A classifier round-tripped through `Export.classifier.toAsset`/`ee.Classifier.load()` only supports `CLASSIFICATION` output mode — `.setOutputMode("MULTIPROBABILITY")` on a loaded asset classifier fails with `Trainer only supports the mode 'CLASSIFICATION'`. Not documented anywhere; found by running it live. Only a classifier trained fresh in the current session supports `MULTIPROBABILITY`. | `scripts/train_landcover_rf.py`: `--with-probabilities` now forces a fresh train (`effective_asset_cache = use_asset_cache and not with_probabilities`) and reuses that *same* classifier for both the hard-label and probability rasters, so the two outputs stay mutually consistent. |
| 2 | `MULTIPROBABILITY`'s band order is undocumented beyond "in class order" — could mean sorted class value or training-data first-appearance order. | Verified empirically: sampled a mixed-landcover region, compared `argmax(probability bands)` against the *same* classifier's own `classify()` hard-label output — 97.2% exact agreement (2479/2550 pixels), mismatches concentrated in built_up/bare near-ties (spectrally similar classes, probabilities summing to exactly 1.0), not a systematic swap pattern. Confirms sorted-class-value order (`prob_vegetation, prob_built_up, prob_bare, prob_water`) is correct. |
| 3 | `export_classified_raster()` had a hardcoded GCS `description`/`prefix` regardless of `out_path` — calling it twice per run (hard-label raster, then probability raster) targeted the exact same GCS blob. Only didn't corrupt anything because the two exports+downloads ran sequentially, each fully completing before the next started. | `description`/`prefix` now derived from `out_path`'s stem, so each export targets a distinct GCS object. |
| 4 | U-Net's training-patch cache (`export_training_patches`, file-existence check only) and model cache (`train_unet`, `.keras`-file-existence check only) are both independent of whether the validation sample (which defines the training-exclusion zone) has changed. After relabeling, `--force-retrain` alone didn't invalidate either — meaning a retrain could silently train on stale, wrongly-excluded patches (real train/test leakage risk against the new validation points), or reload a model actually fit on the old exclusion zone. | Stopgap first: cascaded `force_retrain` into `export_training_patches(..., force=force_retrain)`, added `_clear_patch_dir()` (needed because `export_patches_to_gcs` downloads by matching blob name — a re-export with a *different* shard count than the stale cache would leave orphaned old shards that never get overwritten). |
| 5 | The stopgap (#4) was correct but coarse — forced an expensive GEE patch re-export even for pure hyperparameter-tuning reruns where the validation set hadn't changed at all. | Replaced with proper fingerprinting: `training_fingerprint(validation_csv_path)` (`sha256` of the CSV's bytes) stored in a `source_fingerprint.txt` sidecar next to the exported patches. `export_training_patches` now re-exports only on a fingerprint mismatch (labels actually changed) and reuses the cache for free otherwise — fully decoupled from `--force-retrain`. |
| 6 | Same staleness class one level up: `train_unet`'s model cache didn't know if the cached `.keras` file was trained on the *current* patches. | Extended the same mechanism: `train_unet(..., data_fingerprint=...)` compares against a `<model_stem>_fingerprint.txt` sidecar next to the model file; mismatch → auto-retrain. |
| 7 | One-time gap from applying fix #6: backfilled the model's fingerprint sidecar for the already-trained model (since it genuinely matched current labels), but forgot to backfill the *patch* cache's fingerprint the same way — caused one unnecessary patch re-export on the next run before self-correcting (that run wrote its own fingerprint properly). | No code fix needed — self-corrected after the one extra run. Noted here so it isn't mistaken for a recurring issue. |
| 8 | MLflow 3.x puts the plain flat-file tracking backend (`./mlruns`) into "maintenance mode" and refuses to use it without an explicit `MLFLOW_ALLOW_FILE_STORE=true` opt-out. | Switched to a local SQLite-backed tracking URI (`sqlite:///mlflow.db`) instead of fighting the deprecation — still fully local, no server. Artifacts still land in local `mlruns/<experiment>/<run>/artifacts/` by default alongside it. |
| 9 | Installing `mlflow` downgraded `pandas` (3.0.5→2.3.3) and `protobuf` (7.35.1→6.33.6) in both venvs to satisfy its dependency constraints. | Verified nothing broke before proceeding: `ee`, `google.cloud.storage`, `rasterio`, `sklearn`, and `pandas.crosstab` all still import/work correctly under the downgraded versions, in both the Windows venv and the WSL2 venv. |
| 10 | **The big one.** `build_landcover_ensemble.py`'s own diagnostic printed `Valid in RF only: 10,742,054 (57.9%)` — a huge, implausible coverage gap given both rasters are clipped to the same ~788 km² boundary. Root cause: GEE's export pipeline writes masked/clipped-outside-boundary pixels as **NaN** (not `0.0`) for float32 bands — confirmed empirically (10,670,288 NaN pixels in *every* band of the RF probability raster, identical locations across bands, matching the RF hard-label raster's nodata count exactly). U-Net's probability raster, written locally via `rasterio` rather than through GEE's export pipeline, uses clean `0.0` for the same concept instead. `ensemble.py::load_prob_raster()`'s `.astype(bool)` on the valid_mask band treats NaN as truthy (any nonzero bit pattern), so RF's masked-out pixels were silently read as "valid." The *output* of the first ensemble build wasn't actually corrupted — U-Net's correctly-computed mask happened to "rescue" the result via `combined_valid = rf_valid AND unet_valid` (unet_valid was correctly restrictive, so the AND reduced to it) — but this was a fragile coincidence specific to combining exactly these two rasters, not a guarantee, and the diagnostic itself was actively misleading. | Added `_to_valid_bool()`: `np.nan_to_num(x, nan=0.0) > 0.5`, applied in both the same-grid and reprojection code paths, plus defensive `nan_to_num` on the probability arrays themselves. Added a regression test (`test_load_prob_raster_nan_masked_pixels`) specifically covering GEE-style NaN masking so this can't silently reappear. Rebuilt the ensemble after the fix — diagnostic went from "RF only: 57.9%" to a sane "RF only: 0.2%, U-Net only: 0.0%" (genuine minor edge-pixel differences between the two models' independently-computed footprints, not a systemic bug). |
| 11 | `scripts/run_week1_gates.py`'s G5 comment claimed `member_a_labels`/`member_b_labels` were "placeholder example values... replace with your own before trusting the result." They aren't — confirmed byte-for-byte identical to the real independently-collected joint-labeling values in `notebooks/Colab Notebooks/urban_heat_sg_week1_gates.ipynb` (same arrays, same kappa=0.676 result reproduced locally). The wrong comment had propagated into both `docs/MASTER_PROMPT_2026-07-29_1336.md` and `docs/Progress_Log_2026-07-29_1336.md`, which described G5 as "not yet meaningful." | Corrected the comment in the script and both status docs — G1-G5 all genuinely PASS on real data. |

## 3. Ground-truth relabeling (parallel track, user-driven)

The existing 200-point validation CSV turned out to have been generated
by the labeling app's **unstratified fallback path**
(`worldcover_class_name == "unknown"` for all 200 rows) rather than the
intended WorldCover-stratified draw — discovered during planning, before
any of the code work above. User's decision: regenerate a properly
stratified sample and relabel all 200 from scratch (old labels archived,
not discarded, as `validation_sample_200_labeled_UNSTRATIFIED_v1.csv`).

Final relabeled distribution (200/200, none blank, no points flagged
uncertain): vegetation 105, built_up 69, water 15, bare 11.

## 4. MLflow experiment tracking (new)

- **`src/utils/experiment_tracking.py`**: `start_run(model_name, **tags)` —
  sets a shared experiment (`"landcover_classifiers"`) and starts a
  tagged run. Tracking URI pinned to an absolute path
  (`REPO_ROOT/mlflow.db`) so both training scripts write to the *same*
  store regardless of which OS invokes them — RF runs natively on
  Windows, U-Net runs in WSL2 (via its `/mnt/c/...` mount to the same
  physical repo), and `REPO_ROOT` resolves correctly in both.
- Both `scripts/train_landcover_rf.py` and `train_landcover_unet.py`
  wrapped in `with start_run(...)`, logging: all relevant hyperparameters
  from `config/settings.py`, `n_validation_points`, the CLI flags used;
  `informal_accuracy` + `n_scored`; for U-Net, the full per-epoch
  train/val loss/accuracy curve (when a real training run happened, not
  a cache hit) plus `best_val_loss`; and the output raster(s)/model file
  as artifacts.
- `mlflow.db` and `mlruns/` both gitignored (local-only tracking store,
  same as `.venv/`). Browse with `mlflow ui --backend-store-uri sqlite:///mlflow.db`
  from the repo root.
- Both venvs (native Windows `.venv`, WSL2 `~/venvs/urban-heat-unet`)
  have `mlflow` installed; `requirements.txt` updated (unpinned, matching
  the existing pattern for `folium`/`matplotlib`/`tensorflow`).

## 5. Labeling app UX fixes (`app/pages/1_Label_Validation_Points.py`)

Made while the user was doing the relabeling pass in §3, in response to
live feedback:

- **Map didn't zoom/re-center on the selected point.** `folium.Map`'s
  `location`/`zoom_start` only take effect on the component's very first
  render — `streamlit_folium` otherwise preserves whatever pan/zoom the
  user last had. Fixed by passing `center=`/`zoom=` directly to
  `st_folium()` itself (which does force the view), computed from
  whichever point is currently selected, zoom level 18.
- **Manual click required between every save.** "💾 Save label" now
  auto-advances to the next unlabeled point (same point automatically
  re-centers via the fix above), so labeling 200 points doesn't need a
  separate "jump to next" click after every single save.
- **WorldCover reference hidden entirely** (previously shown as
  "context only, NOT the answer") to remove anchoring bias — a labeler
  seeing a suggested answer before forming their own judgment tends to
  be subtly influenced by it even when told it isn't authoritative.
  Underlying `worldcover_class_name`/`worldcover_class_raw_name` columns
  left in the CSV, just not displayed during labeling.

## 6. Final formal evaluation results

`scripts/evaluate_landcover_classifiers.py`, against the properly
stratified, fully relabeled 200-point set (§3):

| model | accuracy | macro F1 | weighted F1 | vegetation | built_up | bare | water |
|---|---|---|---|---|---|---|---|
| RF | 75.0% | 0.657 | 0.768 | 0.866 | 0.687 | 0.229 | 0.848 |
| U-Net | 78.3% | 0.608 | 0.761 | 0.829 | 0.764 | 0.000 | 0.839 |
| **Ensemble** | **79.8%** | **0.687** | **0.801** | **0.874** | **0.766** | **0.261** | 0.848 |

The ensemble beats both individual models on every aggregate metric, and
on 3 of 4 per-class F1s (ties RF on water). "Bare" is the weakest class
throughout (smallest class, 11 points, spectrally similar to built-up —
already independently confirmed as a real confusion during bug #2's live
band-order check, not a labeling artifact). Full outputs (comparison
table, per-model confusion matrices, per-class metrics) written to
`data/processed/landcover/evaluation/`.

Assessed whether this result warrants redoing labeling or an
inter-annotator cross-check: no — the ensemble consistently improving on
*both* individual models is itself a coherent, expected pattern (not what
you'd see from noisy/inconsistent labels), and separately, a real joint-
labeling crosscheck already exists and passed (see bug #11: G5,
kappa=0.676, substantial agreement) — it just wasn't visible before today
because of the mislabeled comment.
